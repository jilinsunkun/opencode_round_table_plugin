# 状态卡更新规则

## 目标

状态卡用于把每轮圆桌讨论压缩成下一轮可直接续接的最小信息单元。

## 更新时机

每一轮结束后，由主持 Agent 统一更新状态卡。

更新触发条件包括：

- 发散轮结束
- 挑刺轮结束
- 工程评估轮结束
- 研究补充轮结束
- 上下文接近上限需要压缩续航

## 输入来源

状态卡的更新输入来自四类角色输出：

- 发散 Agent：提供新方案、替代路径、补充视角
- 挑刺 Agent：提供漏洞、边界条件、失败场景
- 工程 Agent：提供落地成本、实现路径、验证难度
- 研究 Agent：提供事实、案例、外部依据

## 主持人归并规则

主持人更新状态卡时，只保留能推动下一轮讨论的最小信息。

### 必保字段

1. 当前问题
2. 当前主方案
3. 已否决方案
4. 关键争议
5. 仍待验证点
6. 下一轮需要回答的问题

### 更新原则

- 新信息如果能改变结论，就写入状态卡。
- 新信息如果只是重复描述，不写入状态卡。
- 新信息如果只是背景说明，保留在历史摘要，不写入状态卡。
- 已被否决的方案不要复活，除非出现新的关键证据。
- 争议项要写成可验证的问题，而不是情绪化描述。

## 从四类输出到状态卡的映射

### 1. 发散 Agent 输出

写入：

- 当前主方案的替代选项
- 备选方案池
- 可能的创新路径

处理方式：

- 如果只是重复旧方案，忽略。
- 如果是新路线，加入“已否决方案”或“备选方案”视情况处理。

### 2. 挑刺 Agent 输出

写入：

- 关键争议
- 仍待验证点
- 风险与失败场景

处理方式：

- 能被验证的问题写成问句。
- 无法验证但高风险的点写入关键争议。

### 3. 工程 Agent 输出

写入：

- 主方案的落地路径
- 复杂度判断
- 验证顺序

处理方式：

- 如果工程评估认为主方案不可落地，则将主方案降级到备选方案。
- 如果工程评估提供了更短的实现路径，则更新当前主方案。

### 4. 研究 Agent 输出

写入：

- 支持主方案的证据
- 反例证据
- 可参考的最佳实践

处理方式：

- 只有能改变判断的证据才写入状态卡。
- 仅作为背景的资料放入历史摘要。

## 状态卡压缩规则

当上下文接近上限时，主持人执行压缩：

1. 保留必保字段
2. 删除重复叙述
3. 删除旧版背景说明
4. 只留当前轮仍然有效的信息
5. 历史细节进入 registry 的 history 摘要

压缩后状态卡仍然要能回答：

- 我们在讨论什么
- 现在主方案是什么
- 为什么还有争议
- 下一轮该验证什么

## 输出格式

主持人每轮更新后输出统一格式：

```markdown
# 状态卡

## 当前问题
...

## 当前主方案
...

## 已否决方案
- ...

## 关键争议
- ...

## 仍待验证点
- ...

## 下一轮需要回答的问题
- ...
```

## 纪律

- 状态卡是下一轮唯一的最小输入，不是完整纪要。
- 角色的自然语言输出可以很长，但写回状态卡必须很短。
- 每轮必须先更新状态卡，再进入下一轮。
