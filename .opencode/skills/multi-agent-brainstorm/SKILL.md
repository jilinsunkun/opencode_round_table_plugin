# OpenCode 多 Agent 头脑风暴

这个 skill 用于让多个 agent 围绕**同一个问题**并行发言、互相挑刺、再统一收敛，适合复杂架构设计、算法设计、方案选型和高不确定性问题。

## 核心原则

- 同题讨论，不做任务接力。
- 先发散，再对抗，最后收敛。
- 一定要有反方，否则容易集体自嗨。
- 主持人负责控场和裁决，不亲自包办所有观点。

## 推荐角色

### 1. 主持 Agent

职责：

- 定义问题
- 明确边界和目标
- 控制讨论节奏
- 汇总分歧并收敛结论

### 2. 发散 Agent

职责：

- 从不同角度提出方案
- 优先扩大可能性
- 不急着统一答案

可细分为：

- 激进型：追求上限
- 保守型：追求稳定
- 简化型：追求最短路径
- 性能型：追求效率和扩展性

### 3. 挑刺 Agent

职责：

- 找漏洞
- 找边界条件
- 找失败场景
- 找过度设计

### 4. 工程 Agent

职责：

- 评估可落地性
- 评估复杂度和成本
- 评估维护和验证难度

### 5. 研究 Agent

职责：

- 补充事实、资料和参考案例
- 查同类实现
- 查最佳实践

## 工作流

### 第一步：定题

主持 Agent 先输出：

- 问题是什么
- 目标是什么
- 约束是什么
- 已知事实是什么
- 不能做什么
- 怎么算成功

如果问题有歧义，先指出歧义，再进入讨论。

### 状态卡机制

为避免圆桌讨论在多轮迭代中丢失核心知识，每个角色都要维护一份简洁的状态卡，由主持 Agent 在每轮开始前统一分发。

状态卡固定包含：

- 当前问题
- 当前主方案
- 已否决方案
- 关键争议
- 仍待验证点
- 下一轮需要回答的问题

状态卡不是完整会议纪要，只保留能推动下一轮讨论的最小信息。

### 第二步：并行发散

多个发散 Agent **同时**回答同一个问题，但从不同角度切入。

### 第三步：交叉挑刺

挑刺 Agent 对所有方案进行批判性审查，重点看：

- 最脆弱的假设
- 最大风险点
- 最难落地的部分
- 最容易出错的边界条件

### 第四步：二轮修正

发散 Agent 或工程 Agent 根据挑刺结果修订方案，删除多余复杂度，补足缺口。

### 第五步：主持收敛

主持 Agent 综合所有观点，输出：

- 主推荐方案
- 备选方案
- 选择理由
- 风险与代价
- 下一步验证建议

### 第六步：必要时压缩续航

当上下文接近上限时，不换角色、不换讨论对象，而是先由主持 Agent 压缩状态卡，再继续同一轮圆桌。

压缩后仍然保留：

- 当前问题
- 当前主方案
- 已否决方案
- 关键争议
- 仍待验证点
- 下一轮需要回答的问题

### Session Registry

如果需要长期圆桌讨论，建议使用项目级 Session Registry 保存固定角色与 session 的绑定关系。

建议文件：

- `.opencode/brainstorm/registry.json`

Registry 的职责：

- 记录 topic
- 记录角色与 session 的绑定
- 记录当前轮次
- 记录状态卡
- 记录压缩与续接标记

Registry 的原则：

- 角色绑定默认不可变
- session 绑定默认不可变
- 只有上下文损坏、用户明确要求或议题切换时才允许重建

### 状态卡更新规则

状态卡更新规则单独存放在：

- `.opencode/brainstorm/state-card-rules.md`

主持 Agent 每轮结束后必须按该规则把四类角色输出归并为新的状态卡，再进入下一轮。

### TS 硬约束

如果插件已经提供 TypeScript 校验与 registry 写入能力，则优先依赖插件做硬约束；skill 只负责解释规则，不负责执行校验。

## 提示词模板

### 主持 Agent

```text
你是主持 Agent。请先把问题定义清楚，不要急着给最终答案。

请输出：
1. 问题定义
2. 目标
3. 约束
4. 已知事实
5. 不能做的事
6. 评估标准

如果问题有歧义，先指出歧义。

请在每轮开始前生成并分发状态卡，确保所有固定角色都能继承上一轮的讨论结果。
```

### 发散 Agent

```text
你是发散型 Agent。请围绕同一个问题，从你的角度独立提出一个方案。

要求：
- 先发散，不要急着收敛
- 只输出你自己的方案
- 给出优点、风险、前提假设

如果主持人提供了状态卡，请优先基于状态卡继续讨论，不要重新从零开始。
```

### 挑刺 Agent

```text
你是挑刺型 Agent。请对现有方案进行批判性审查。

重点找：
- 漏洞
- 边界条件
- 风险点
- 过度复杂的地方
- 没有说清楚的地方

如果主持人提供了状态卡，请优先攻击状态卡里仍待验证的关键假设。
```

### 工程 Agent

```text
你是工程可行性 Agent。请从实现角度评估方案。

重点看：
- 复杂度
- 依赖成本
- 维护成本
- 验证难度
- 是否建议采用

如果主持人提供了状态卡，请优先判断当前主方案的落地成本与验证路径是否合理。
```

### 研究 Agent

```text
你是研究型 Agent。请补充与当前问题直接相关的事实、参考案例或最佳实践。

要求：
- 只给直接相关的信息
- 不要泛泛而谈
- 如果有成熟做法，请明确指出

如果主持人提供了状态卡，请优先补充能帮助验证“仍待验证点”的事实或案例。
```

## 最终输出格式

建议固定成下面这 5 项：

1. 主方案
2. 备选方案
3. 关键取舍
4. 风险与代价
5. 下一步验证

## 使用建议

- 适合复杂架构设计、算法设计、方案对比、系统重构。
- 不适合很简单的小问题，简单问题直接单 agent 更快。
- 如果讨论开始跑偏，主持 Agent 应立即重述问题。
- 如果需要多轮圆桌讨论，必须使用状态卡维持知识连续性，避免每轮重新起跑。
